Qwen3.6-35B-A3B Platform

AWS Deployment Architecture

SGLang · graph MCP harness · continuous RL hot-swap — 3k DAU / ~750 concurrent / 30k conversations/day / 2–8 s response SLA

A3B = Mixture-of-Experts: 35B total parameters, ~3B active per token. VRAM is sized by total params (~35 GB at FP8) but compute and memory bandwidth by active params — so decode runs ~4–5× faster than a dense 35B and each replica fits on one H100 at TP=1. Live fleet drops from 6× H100 to 3× H100. Replica count is now set by the latency SLA, not throughput.

MoE halves the fleet

  • • VRAM by total params: ~35 GB FP8 → fits 1× H100, TP=1
  • • Bandwidth by active params: 3 GB/token, not 35
  • • Decode ~4–5× faster than dense 35B — ~200 tok/s single-stream
  • • KV ~48 KB/token → ~96 slots per replica at 8k ctx
  • • BF16 would not fit (70 GB weights, 2 GB KV left) — FP8 is required for TP=1

Latency sets replica count

  • • Throughput needs 1 replica; the 8 s SLA needs 2
  • • 1 replica → batch 25 → 120 tok/s/stream → ~8.5 s, breaches
  • • 2 replicas → batch 12 → 180 tok/s/stream → ~6.4 s, meets
  • • The 6-iteration cap breaches 8 s (~9.6 s) — needs a wall-clock deadline, not just an iteration cap
  • • SSE streaming makes TTFT ~2.6 s — the highest-leverage fix

Sizing basis

  • • 30k conversations/day × 2.5 passes = 75k calls/day
  • • Decode 30M tok/day → ~1,200 tok/s peak
  • • Prefill 306M uncached → ~150M with prefix cache
  • • Little's Law: ~25 streams generating, not 750 — session count never drove sizing
  • • Prefix affinity at the inference LB is load-bearing, not an optimisation

AWS footprint

  • • 1× p5.48xlarge carries live (3 GPU) + canary (1 GPU), 4 spare
  • • Price against Capacity Blocks / Savings Plans — on-demand p5 is the worst rate
  • • g6.4xlarge for the scheduled ML model (exact spec match)
  • • c7g.2xlarge = the 8 vCPU graph weight worker
  • • Data tier is small: ~220 GB/yr Postgres, ~500 GB/yr vector, ~45 GB/yr graph

Training on one GPU — verdict

  • • LoRA RL fits: ~66 GB on 1× H200 (141 GB) or B200 (180 GB). ~600–1,200 steps/day
  • • Full-param RL does not: ~520 GB. AdamW FP32 state alone is 280 GB
  • • With LoRA the KL reference model is free — base weights, adapters disabled
  • • LoRA continued pre-training viable: ~1.9 B tok/day H200, ~4.3 B B200
  • • From-scratch pre-training: 1.3–2.9 yr on one GPU. Not feasible

Open risks

  • • AWS sells no single H200 or B200 — both are 8-GPU SKUs. Use the 4 spare H100s on the p5 already in the plan rather than buying an instance
  • • Training and serving would then share a machine — pin GPUs so a training job cannot breach the 8 s SLA
  • • Graph weight calc: 8 vCPU is fine incrementally, not for global PageRank over 110M nodes
  • • Continuous graph ingestion needs a retention/decay policy from day one
  • • p5e (H200) is worth pricing for serving too — ~1.43× decode, ~5.2 s end-to-end
